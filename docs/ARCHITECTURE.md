# FlowGuard architecture

## Ownership

Tauri manages windows and trusted commands. Rust `SharedState` owns the persisted document, preferences, selected connection, observation snapshots, bounded history and scene description. Each WebView mirrors a revisioned snapshot and sends commands. Local form drafts and search text are presentation state; no native window owns the document. Browser preview is an isolated demo adapter with a different storage namespace.

Mutations are serialized through a mutex. Document changes are written to a sibling temporary file, flushed, then atomically renamed. A failed write restores the in-memory document and selection. Events broadcast after a successful commit. Clients reject older snapshot revisions. The observer runs outside the UI thread and outside the state lock; observation tool execution has a six-second deadline and bounded output.

The inspector can dock left/right or become another Tauri WebView. Closing its floating window restores the docked state. Restart resets the panel to a docked position. Current docking uses explicit placement controls; Adobe-style drag-to-dock tab groups and arbitrary panels are not implemented.

## Observation is not enforcement

`socketfilterfw --getglobalstate` reads the standard macOS firewall state. `lsof -nP -iTCP -sTCP:ESTABLISHED -FpcnPt` reads sockets visible to the current account. Arguments and absolute tool paths are fixed. Neither command writes settings, invokes a shell, requests root privileges, resolves domains, or captures packet payloads. macOS `proc_pidpath` resolves an executable path when permitted.

This observes a subset of established TCP sockets, not every packet, every application or short-lived connection. Socket direction is `unknown`: local/remote endpoints alone cannot determine who initiated a connection. History records first detection; polling is not continuous capture. Permission errors and unsupported platforms must not be reported as complete observation coverage.

A saved rule is an intention only. Matching includes data source, verified signing subject (live) or executable path (demo), exact destination, port and direction. Specific-direction rules take precedence over a both-direction fallback, then the newest rule. Unknown observed direction only matches a both-direction rule. Demo rules cannot enter the Swift enforcement policy. Unsigned enforcement remains unavailable. A signed runtime can report a correlated provider acknowledgement separately from stored intentions; it does not prove a particular flow was blocked.

## Network Extension candidate

`native/FlowGuardFilter` contains a Swift policy library and an `NEFilterDataProvider` subclass. It compiles against the local macOS SDK. Candidate policy evaluation uses an audit token and Security framework to verify the running signing subject, exact remote endpoint and actual extension-provided traffic direction. An explicit TCP rule dispatches new flows to the provider. The implementation supports allow/drop/ask. Matching signed TCP flows pause for an authenticated, one-flow decision. AskQueue bounds pending requests to 128 and records at most 64 outcomes. Each request captures its 15-second fallback: allow by default, or block selected by the user. Real OS pause/resume and lifecycle behavior remain Pending.

The package now includes an executable extension target, a compiled activation/configuration API, signature-gated host IPC and a versioned acknowledgement contract. The unsigned staging script embeds the extension and helper but does not install entitlements or activate them. The desktop calls a bundled Swift runtime through a versioned C ABI for activation and uses fixed-helper status/sync commands. Rust owns lifecycle and policy receipt state; all WebViews display the same revisioned snapshot. The unsigned runtime rejects activation before calling OS configuration APIs.

Before deployment, configure approved signing profiles and verify IPC identities in a real signed environment; provide decision request/resume messages; implement automatic resync, startup-policy refresh for subsequent edits and uncertain-timeout recovery. Do not enable an extension just because its source compiles.

Apple references: [NEFilterDataProvider](https://developer.apple.com/documentation/networkextension/nefilterdataprovider), [flow pause semantics](https://developer.apple.com/documentation/networkextension/nefilternewflowverdict/pause%28%29), [Network Extensions for the modern Mac](https://developer.apple.com/videos/play/wwdc2019/714/).

## GPU boundary

The compact communication diagram is currently a bounded code-native UI graphic in the WebView. Rust owns the renderer module and capped scene descriptions. The optional `gpu` feature implements a wgpu/Metal route pipeline, bounded mesh tessellation, resize handling and a GPU-owned render target. The native compositor connection remains unfinished; the default build does not initialize this renderer.

GPU commands, geometry, buffers and textures remain in Rust/wgpu. JavaScript receives application state, identifiers and small scene metadata, never image buffers or rendered frames. There is intentionally no GPU readback or frame IPC API. The Metal smoke check submits a route to the GPU-owned texture without exporting pixels.

## Local data

Rules and preferences are stored under Tauri's application data directory. JSON backups contain legacy executable paths, signed subject identities and destinations. History is in-memory only (up to 500 first-seen entries per session) and clears at exit. No remote backend, analytics, telemetry, credential storage, reverse DNS or threat service is connected. Restore validates schema, enum values, bounds and duplicate IDs; the UI offers one-step undo. A separate stable `.lock` file is held with an OS advisory file lock for the document lifetime; another compliant FlowGuard process is rejected before loading or writing. Rule mutation requests carry the rule list they were based on, compared inside the session mutex before persistence. Conflicts emit the latest snapshot and reject the stale request. Undo carries the post-operation rules as its baseline, so later edits cannot be overwritten. Legacy builds that do not use this lock must be closed before running this version. Native application groups are projected by Rust using executable paths; unidentified processes stay separate. Live enforcement identity uses verified signing subjects; real signed deployment verification remains Pending.


## Unsigned native packaging increment

The Swift package now builds `FlowGuardSystemExtension` and `FlowGuardBridgeCLI`. `npm run native:package` stages an unsigned app copy with the executable extension under `Contents/Library/SystemExtensions` its helper under `Contents/MacOS`, and `libFlowGuardHostRuntime.dylib` under `Contents/Frameworks`. Provider registration uses the explicit Objective-C name `FlowGuardFilterDataProvider`. This native package requires macOS 13 for public XPC signing requirement APIs.

The shared bridge contract uses protocol v3, request UUID, per-process provider instance UUID and expected revision. The running provider's receiver serializes validation and replacement, rejects demo or invalid policies and preserves its previous revision when application fails. The signed helper authenticates the provider, the provider authenticates the helper, and the helper authenticates its signed desktop parent. Anonymous XPC tests exercise the same contract without starting the production listener or weakening its signature requirements.

Rust loads the fixed bundled runtime, checks ABI version 3 and retains it for asynchronous callback lifetime. Swift dispatches signed activation onto the main queue. Activation callbacks are correlated to the current operation; approval and configuration persistence never imply policy application.

Sync records the exact live-rule snapshot sent to the provider. Only a correlated acknowledgement whose rules still match the current document yields `applied` and per-rule receipt badges. Concurrent edits yield `stale`; disconnect or a different provider instance/revision clears confirmation. Status refresh polls every five seconds when signed and idle, and never restores a lost receipt merely from a revision number. Receipts are session-local. Failures may leave an older policy active, which the UI explicitly explains. No automatic resync or uncertain-timeout reconciliation is implemented yet. All signed sandbox/IPC and OS-filter behavior remains Pending. See `native/FlowGuardFilter/README.md` for reproduction commands.

## Initial policy and removal

Activation captures validated live rules under the Rust document lock before any OS request. C ABI v3 copies bounded JSON into Swift. The host saves it as Data in `NEFilterProviderConfiguration.vendorConfiguration`; the provider validates and loads it before applying network settings or announcing startup. Missing, duplicate, demo, invalid and oversized initial policies fail startup rather than silently substituting an empty policy. This configuration persists locally in macOS preferences. See [Apple vendorConfiguration](https://developer.apple.com/documentation/networkextension/nefilterproviderconfiguration/vendorconfiguration).

After configuration save, Rust keeps the activation operation busy, probes provider readiness up to ten times, and sends one correlated policy update. An uncertain update is never automatically repeated. The acknowledgement is compared with the current document, so edits during approval or synchronization produce stale state. A reboot-required activation does not initiate sync; resumed activation remains explicit.

Disable loads only our configuration, saves `isEnabled=false`, then reloads and verifies before reporting `disabled`. Removal follows disable, deletes our preferences and submits System Extension deactivation; OS failure, approval and reboot requirements remain distinct from completion. An absent disabled configuration skips the unnecessary save. Another provider or unidentified enabled configuration is rejected. Rust clears receipts and suppresses provider polls after confirmed disable/removal; saved document rules remain intact. A disabled setting is not proof that an existing connection has resumed.

Subsequent manual rule sync currently changes the running in-memory policy only. On provider restart the bootstrap rules from the last activation may return, not the last manual sync. Keeping OS bootstrap configuration current and reconciling after restart are high-priority next work; signed production use is not validated.

## Investigation workspaces

Navigation separates Firewall, Network investigation, Server review and Security diagnostics; settings are shared. The Rust observer reads `/sbin/ifconfig -a` with the existing bounded command runner, outside the state lock. The shared network snapshot contains address rows, observation time and an explicit failure state. A failed observation clears previous rows. IPv6 scope identifiers are retained; UP/DOWN reflects the interface flag, not reachability. This read-only step sends no probes and changes no network settings.

The native interface sheet is independent of Firewall demo/observation mode. Browser preview has no synthetic interface records. Server review and Security diagnostics currently show planned capabilities only. Port checks, remote authentication and security assessments are not implemented.

LAN discovery uses explicit Tauri start/stop commands. Rust validates the selected interface/address against fresh interface data and limits active discovery to private IPv4 subnets /24–/30 on active `en` interfaces. It derives targets itself rather than accepting arbitrary target lists or shell arguments. One ping per target is bound to the selected interface, with four concurrent children and bounded command output/runtime. IPv6 uses NDP cache collection only. ARP/NDP entries are evidence of cached neighbors, not proof of reachability. Incomplete and multicast records are excluded. Distinct interface/address rows are not merged by MAC, and hostnames are not inferred from addresses or MACs.

A shared operation number fences stale callbacks. A cancelling job blocks new starts until bounded work finishes; published rows freeze at stop. Periodic interface snapshots do not replace discovery results. Interface/address/mask changes interrupt the worker and mark completed earlier results stale; a network change retaining the same tuple (e.g. the same address on another Wi-Fi LAN) is not yet detectable. Results are memory-only and capped at 1,024 rows. Browser preview never performs collection; visual QA fixtures are temporary and not shipped. The diagnostic command runner captures bounded stderr so ping permission failures are not reported as device absence.

Name enrichment is opt-in per discovery job (`none`, `mdns`, `system`). Up to 64 eligible address rows are queried with four concurrent lookups; other rows explicitly show unsupported scope or the limit. The selected mode and name-query progress live in Rust shared state. Stop freezes both rows and progress, fencing late results. mDNS uses the macOS DNS-SD PTR API with ForceMulticast and an exact interface index, rejects another interface's replies and record removals/zero TTL, and processes replies with a one-second poll deadline. PTR wire data rejects compressed pointers, truncation and control characters. The SDK exports DNS-SD via libSystem.

System mode uses bounded `dscacheutil` calls for private IPv4 rows. A name is accepted only from an output record containing that exact address. Its source is labelled system resolver, because the underlying OS cache, DNS or mDNS source is not known. It can query configured DNS servers outside the LAN; the UI explains this before selection. Each name carries its own collection time and status, separately from neighbor/reachability evidence. Names are untrusted reported information, never stable identity or proof of safety. IPv6 address discovery remains cache-only; optional mDNS name lookups do not add address rows.

## Recollection comparison, details and CSV

Rust `Inventory` owns the last complete baseline, comparison rows, selected address-record ID and LAN panel placement. A complete, error-free result becomes the next baseline; comparison requires identical interface, local address, mask, collection range, active/cache mode and name mode. Changed information includes MAC, reported-name value/source/status, response evidence and evidence source. Observation timestamps alone do not change the classification. Old rows not returned are `not_seen`, preserving their prior observation times, never proof of device absence. Partial, cancelled and failed runs are not promoted and do not infer missing rows. Known network changes invalidate the baseline. At most 1,024 current and 1,024 previous-only rows are exposed. Baselines are memory-only.

The `lan-details` WebView mirrors the same Rust selection and receives revisioned snapshots, with no document or inventory ownership. It docks explicitly beneath the sheet or floats in its own window. Closing it restores docking; restart defaults to docked. Drag-based docking remains future work.

The CSV command checks the collection generation and terminal state while holding the state lock, then serializes all rows independently of presentation search filters. It uses fixed English field/status identifiers, Unix seconds, UTF-8 BOM and CRLF, with quoted cells and neutralized leading formula characters. It includes scope, result quality, changed fields and current/prior evidence. No arbitrary filesystem path is accepted; the WebView requests a normal Blob download, as with rule exports. The macOS unsigned app's CSV download path was verified.


LAN TCP jobs and result rows live in Rust Session. Targets resolve from the current discovery generation; arbitrary and historical addresses cannot be supplied as scan targets. IPv4 /24–/30 scope validation uses the fresh interface snapshot. socket2 binds the source IP and macOS interface index before a 600ms TCP connect; sockets drop without application payload. Four bounded workers publish each batch with operation fencing. Discovery is blocked during a TCP job. WebViews own only range/filter drafts; results include collection generation and explicit stale warnings.


TCP presets (2026-10-13): the fixed JSON catalog is compiled into Rust and imported by the WebView. Rust validates the selection; ranges retain the 256-port limit. A scan snapshot captures its operation ID, LAN generation, source address and requested port vector. UI search/status/sort operate on the mirrored metadata only. CSV is generated under the Rust state lock, exports all observed rows with interruption/stale-collection context, and rejects a request for another operation or an in-progress/empty job. This prevents a rescan within the same LAN generation from exporting the wrong result. CSV cell escaping is shared with the inventory exporter.


TCP comparison and navigation (2026-10-13): Session owns a bounded one-result comparator keyed by target/source IP addresses, source mask, interface, requested port vector and inventory generation. Complete jobs become baselines; cancelled/failed/incomplete jobs do not. A comparison involving either an unknown outcome is uncertain, never a closed-port inference. Only open/refused transitions are definitive; elapsed time and timestamps do not determine change. Baselines hold no nested comparison history and are invalidated on scope/network/collection changes. Comparison metadata travels with snapshots and CSV.

The open_lan_ports command validates a current supported IPv4/IPv6 record, shares its selection, sets the network category and increments a Rust navigation counter without starting a probe. The main WebView reacts to the counter only to scroll/focus the sheet. Floating details reveal/unminimize/focus the main window, recreating it from the configured main window if absent. Each new WebView loads the existing Rust snapshot; no window owns job state.


LAN IPv6 TCP (2026-10-14): only an exact current inventory record may be checked. Rust accepts link-local, ULA and 2000::/3 literals with no zone or the selected interface name as zone. A fresh UP IPv6 address on that same en interface must share its /64–/128 prefix with the target. Source selection prefers the inventory anchor, otherwise the lowest compatible address. Tentative, duplicated, detached and deprecated interface addresses are excluded. Numeric zones are not accepted. No IPv6 address enumeration is added.

The IPv6 socket uses IPV6_V6ONLY and the macOS bound-interface option. Link-local source and destination sockaddr scope IDs use that interface index; literal source binding prevents fallback to another family/source. Source disappearance or prefix changes invalidate the plan. Comparison keys use canonical IpAddr values plus interface and prefix, while UI matching normalizes equivalent IPv6 spellings. Snapshots and 26-column CSV include family and source prefix. Configured-prefix matching is a bounded policy, not proof of physical topology; real LAN routing and address rotation remain unverified.


Service evidence (2026-10-14): Session owns a separate job, operation counter, plan, cancellation flag and selected port. start_services accepts only an existing completed port operation and a fixed protocol mode. Plan revalidates a current discovery record against fresh interface data, keeps only open rows (1–64), and requires the same source IP/prefix as the TCP observation. Discovery, TCP checking and service checking cannot run concurrently. Updates are fenced by operation, collection and source-port operation; cancellation freezes already published rows and ignores late batch results. Known source/network changes invalidate retained evidence. WebViews own only method/filter drafts and mirror the shared selection.

Service sockets reuse the same literal source and macOS interface binding, including IPv6-only mode and link-local scope IDs. Two workers run at a time with a 1.5-second per-endpoint budget including the 600ms connect limit and an 8KiB response cap. HTTPS uses nonblocking rustls I/O with a deadline around each retry, the system trust roots and IP certificate identity verification. No custom verifier or production test root is installed. A fixed HTTP HEAD / request uses the literal target as Host, with no redirect, authentication or DNS lookup. SSH/SMTP receive greetings only; generic 220 greetings are not assumed to be SMTP. Auto mode contacts only supported default ports; unsupported ports retain a candidate and explicit not-attempted status. Explicit modes apply to all open ports.

Only a matching protocol response confirms service evidence. A Server header or SSH software string is labelled self-reported; binary/unrecognized/capped/partial responses cannot supply a product identity. Only bounded sanitized status/banner and Server metadata reach the WebView, not whole response bodies. TLS trust/connection errors remain unconfirmed. The initial sheet is one address/port per row, with search, status filter, sorting, inline docked detail and 20-column Rust CSV. CSV exports all published rows under the state lock and rejects in-progress/empty/old operations; shared escaping handles untrusted reported strings. Hostname/SNI input, certificate detail/expiry display, service comparisons, new floating details and authenticated internal service inspection remain planned.


Software updater (2026-10-14): Session owns the updater state machine, operation fence, retained plugin Update and immutable Rust download bytes. Preferences gain a backward-compatible autoUpdates boolean defaulting true. Release builds check the fixed stable GitHub endpoint after 30 seconds and every six hours; debug builds make no automatic request. The global notice navigates to/focuses the Settings update panel using presentation-only intent. Custom Rust commands handle checking, bounded downloading, cancellation and installation; the WebView receives no artifact bytes or signature/private-key material and has no plugin-updater permissions.

HTTPS/source/version restrictions precede download; minisign, trusted-comment version binding and bounded archive identity/path validation precede Ready. Operation fencing rejects callbacks after cancellation. Only the install command takes a Ready artifact, after job/extension gates, then blocks document writes/new jobs. A sibling backup survives the plugin's own temporary-backup errors; installation is followed by codesign, matching Team ID and Gatekeeper checks, with restoration on failure and restart on success. Stored rules/preferences stay outside the replaced bundle. Real signed-app replacement remains Pending; disposable mock-app installation and rollback are tested.

The updater public key is embedded in config; its long-lived private key is local, permission-restricted and ignored by Git. Release preparation signs/notarizes/staples before producing the updater archive and version-bound signature. Publication is explicit, never overwrites existing versions, and uploads only public distribution assets. CI runs tests; it does not receive signing credentials or publish builds.


Normal policy application persists the validated startup policy through the in-process Swift host (C ABI v3) before the helper performs live XPC synchronization. Preference reload must confirm ownership, enabled state and exact payload. Rust holds the extension operation busy throughout both phases and marks application only after the correlated provider acknowledgement. Persistence callback tokens are independent of activation callbacks and expire after 30 seconds; late replies are discarded. OS save and live application are not an atomic transaction: a failed live sync leaves a persisted startup policy and requires later reconciliation.

Recovery intent is session-local and captures the last explicitly requested live policy. Provider status contains a SHA-256 digest over a domain-separated stream of length-prefixed UTF-8 rule fields in policy order. Swift initializes that status from the actual startup policy; updates change rules/revision/digest under the receiver lock. Rust compares exact policy contents via the same digest before recovering a lost receipt. No rule payload is added to the UI snapshot. Recovery waits for authenticated ready status, confirms persisted startup policy, skips redundant replacement on a matching digest and otherwise uses the correlated update contract. Current edited rules must still equal recovery intent. Shared-state admission rejects busy operations and installation. Failed recovery attempts wait 10/20 seconds between attempts and stop after three attempts; manual apply resets the budget. Disabling/removing clears intent before any asynchronous OS request. Legacy providers without a digest are rejected for reconciliation.

### AI Security normalization foundation

`security.rs` defines independent SecurityFlow/SecurityEvent/RouterCapabilities models. Session snapshots derive a bounded, deduplicated read-only view of the currently visible socket samples under the existing shared-state lock. Source-qualified IDs distinguish demo and local Mac records. `firstObservedAt` is the first retained socket observation; `sampledAt` is the successful collection time, not a connection-start time. Initiator direction and byte counters remain unknown/unavailable. No router connection, detection, LLM call or enforcement is introduced by normalization. Router data must later retain its real source identity and optional application attribution; it must not create fictional macOS processes. This initial view is session-only and is not persisted into the rule document.

### Signed rule subjects and legacy migration (2026-10-14)

Connection.appKey remains the observed executable path for display/grouping; Connection.identity is optional and is populated only by Security.framework verification of a running guest. Live Rule.appKey is the canonical `signed:v1:authority:team:identifier` subject key, and Rule.identity must agree with it. Apple binaries must satisfy `anchor apple and identifier`, developer binaries `anchor apple generic and certificate leaf[subject.OU] and identifier`. Claimed identifiers/Team IDs alone are insufficient. Identifier text is bounded and restricted before requirement construction; arbitrary requirement expressions are never imported. Helpers are identified by their actual code-signing identifier, which need not be the parent app's Info.plist Bundle ID.

SaveRule and MigrateRule reacquire the running guest and compare it to the observation under the existing shared-state transaction. MigrateRule accepts only an existing live identity-less rule and a current connection with its old path/destination/port. It preserves intent, destination, direction and original rule ID, rejects an occupied signed scope, and uses the existing expected-rules conflict check and atomic persistence rollback. Undo restores the inactive legacy rule. No trust is retroactively inferred from a current file at an old path. Legacy rules remain readable/exportable but are excluded from provider payloads, recovery targets, digests and acknowledged IDs. Demo rules remain isolated path-based intentions.

The provider independently verifies each flow's audit token using SecCodeCopyGuestWithAttributes and SecCodeCheckValidity against the same canonical anchors/subject constraints. It never falls back to executablePath when identity is absent. A missing/invalid identity means no matching rule; the provider's existing unmatched default is allow. Signature verification does not rate a binary's behavior or code loaded by an interpreter.

Protocol v3 and the FlowGuardPolicy/v3 digest include all signing identity fields and timeoutAction. The OS initial-policy key is flowguard.initialPolicy.v3. Saving removes both obsolete v1/v2 slots and verifies absence after reload. Old provider replies and initial policies are rejected. Exported backups use version 3; versions 1/2/3 import under the current validator, quarantining identity-less live rules and defaulting missing timeoutAction to allow. Replace host/helper/extension together; source edits do not deactivate an installed old provider. Downgrade is unsupported.

### Ask decisions

Swift owns the flow callbacks and ContinuousClock deadlines (advancing across sleep); Rust owns the shared desktop inbox and operation fencing. A separate one-second polling loop uses the fixed signed helper and authenticated XPC pendingAsks/answerAsk methods. Answers bind provider instance, policy and request UUID, accept only allow/block and resolve once. The queue validates deadline under its lock; a late answer cannot override fallback. Policy replacement and graceful stop drain with captured fallback; capacity/inactive intake uses it immediately. Callbacks execute outside locks. UI displays approximate time, signer, scope, captured fallback and one-flow buttons; no permanent rule is created by answering. Provider acknowledgement/outcome records are not proof of OS network behavior.

Preferences default to allow after 15 seconds to avoid interrupting legitimate traffic when no UI answer is available. Users may select block. Changing the preference updates all saved ask intentions atomically under document conflict control and clears application receipts; explicit apply is required. Already pending requests retain their captured policy. Rust fences stale polls and responses and atomically claims requests across windows. Unknown replies are reported as uncertain, never success. Crashes, actual OS resume ordering, sleep/wake and transport/signing installation integration remain Pending.
