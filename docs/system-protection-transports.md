# システム保護のプロトコル・管理経路仕様

更新: 2026-10-16。識別と例外の設計は確定。UDP処理・管理セッション保護の実装と署名済み実通信は未完了。

## 現在の実装境界

v4ルールはTCP専用。ProviderのOS登録もTCPのみ。`FlowIdentity`は実フローのtransportを必須とし、TCP以外にはTCPルールのallow/block/ask・システム保護・保護例外を適用しない。askキューもUDP・不明なtransportを拒否し、タイムアウト処理にも入れない。これは未対応通信を安全と判断する処理ではない。Provider入口の未対応フローは従来通りallowで通過し、監視・保護済みと表示しない。

RustとUIのプリセット判定もtransportを明示必須とする。観測フローは観測したprotocolを渡す。保存済みv4ルールだけは契約上のTCPを明示して扱う。protocolが欠落・不明・未対応ならプリセット対象にしない。非TCPの観測からTCPルールの保存・旧パス移行を要求しても拒否し、画面上でも既存TCPルールとの一致を表示しない。OSから得た値と、JSON／表示名／ポートから推定した値を混同しない。

現時点の既定保護は、検証済みApple署名と正確な署名識別子を持つmDNSResponderの送信TCP/53、softwareupdatedの送信TCP/443だけ。DNS全体、mDNS、管理接続全般や通信内容の安全性は保証しない。

## UDP拡張の識別条件

以下は将来の実装条件であり、現行プリセットを広げる設定ではない。

| 対象 | 必須の根拠 | 自動的に認めない範囲 |
| --- | --- | --- |
| Appleリゾルバーの送信UDP DNS | OS由来のUDP、実送信方向、audit tokenから検証したApple署名＋正確な識別子、正規化した送信先IPとポート53 | ポート53だけのアプリ、第三者の同名識別子、暗号化DNS全般、受信パケットの正当性 |
| mDNS送信の初期対象 | 上記の署名根拠、UDP、送信方向、宛先224.0.0.251／ff02::fbと5353、OSが示すインターフェース／IPv6スコープ | 名前が`.local`だけの宛先、任意LANアドレス、受信側全許可、ポート5353だけのプロセス |
| mDNSのユニキャスト応答・受信 | OSの送受信フロー対応と要求に対する応答である根拠を追加して別仕様にする | ローカル受信プロセスの署名を、送信元機器の認証の代わりにすること |
| ソケットで宛先が変わるUDP | OSから得た各宛先とインターフェースを再評価できること | 最初の宛先への許可をソケット内の全送信先へ拡張すること |

パケット単位の情報やインターフェースをProviderから取得できない場合、推測で補わない。初期実装で範囲を保証できないケースは未対応のまま残す。mDNSのlink-local性はパケットの本人性・内容の信頼を意味しない。hop limit等のパケット根拠が必要な判定は、取得可否を実機で確かめるまで有効化しない。

`sourceAppAuditToken`が代理プロセス・VPN・プロキシ等で誰を指すか、ソケットのメタデータがいつ揃うかは実機検証項目。欠落したaudit token、名前だけの識別、PID再利用、パス一致、MAC／PTR一致では署名要件を満たさない。プロセスの署名は宛先サーバーの認証にもならない。

## 管理経路の保護

管理通信は既定プリセットにしない。SSH／HTTPS／画面共有に使われるポートやプライベートIPだけでは、管理者の操作と通常通信を区別できない。

将来の管理経路保護は、ユーザーが選んだ稼働中の管理セッションへの一時的な許可として実装する。以下をすべて満たすこと。

1. ローカルの署名主体、実フロー方向、TCP/UDPの別、送信先IP／ポート、送信元／インターフェースを固定する。SSHなら確認済みホスト鍵、HTTPSなら検証済みの名前／信頼根拠など、選択セッションの相手をユーザーが確認した根拠を別途保持する。単なる到達やServerヘッダーでは代用しない。
2. RustがセッションID、Providerの稼働世代、ネットワーク世代、有効期限を管理する。有効期限は単調時計で最長10分、明示的な再承認で更新する。保存ルール・バックアップに永続化せず、再起動時に復元しない。
3. 相手の鍵／名前／IP、署名主体、経路、Provider世代の変化、セッション終了、期限切れで許可を失効する。識別や有効期限の根拠を失ったときに許可範囲を広げない。トンネルの内側の通信と外側の接続を自動的に同一視しない。
4. 許可の範囲・残り時間・失効を確認でき、個別解除できる。適用中の状態はProviderの世代付き受領確認を要し、保存した意図を適用と表示しない。
5. FlowGuardの全解除はこの許可とは独立した既存の緊急復旧経路を使う。復旧が管理接続やDNSに依存しないことを検証する。

この一時許可の受付・保存・Provider連携・UIは未実装。現在のアプリが管理接続を自動で継続させるとは表示しない。

## ルールとブリッジの移行条件

UDPを有効化するには別のブリッジ契約が必要。新契約はprotocolと必要なendpoint／interface／scope条件をルール・例外・ask要求／回答・ダイジェスト・適用確認へ含める。欠落フィールドをTCPや全プロトコルへ補完しない。旧v4を読み込む移行はTCPとしてのみ明示変換し、新旧Providerの能力が違う場合は適用を拒否する。管理一時許可も別能力として交渉し、UDP対応から管理保護能力を推測しない。

既存のTCP例外をUDPへ複製しない。mDNS例外は将来、署名主体・protocol・方向・宛先・インターフェース／スコープと単位を明示して個別レビューする。一般ルール／例外／管理許可の優先順位を新契約で固定し、OSへ広いUDPルールを登録する前に初期ポリシーと実能力の一致を確認する。詳細な受信・ソケット単位挙動が未確認のままUDPのaskを有効化しない。

## 根拠

- Appleの[`socketProtocol`](https://developer.apple.com/documentation/networkextension/nefiltersocketflow/socketprotocol)はソケットのprotocol値、[`NEFilterFlow`](https://developer.apple.com/documentation/networkextension/nefilterflow)はdirectionとsource app audit tokenを提供する。それぞれは別の識別根拠として扱う。
- Appleの[`localEndpoint`](https://developer.apple.com/documentation/networkextension/nefiltersocketflow/localendpoint)は最初のフロー通知時に未設定の場合があると明記する。メタデータの欠落を既定の安全値に置き換えない。
- [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html)のmDNSの宛先・ポート、複数インターフェースとセキュリティ上の前提を参照。プロトコルの定義と、このアプリの実機で確認できた範囲は分離する。
